# Threading

Describes which thread runs each piece of work a read or a write does on a `HardwoodContext`: the context's pool for CPU work, a read's planning included, virtual threads for I/O, the caller's thread for the read loop, and a context of zero threads, whose reads run on the threads driving them. States the invariants that keep a pool thread from waiting and the context's thread count a bound on a read's CPU.

## Carriers

A read uses two resources of its context: CPU time and requests in flight. Each kind of work runs on the carrier that matches the resource it uses.

| Resource | Carrier | Bound |
|---|---|---|
| CPU: plans, scans, decodes, fills, and applying their results | the context's pool of `n` platform threads; on a context of zero threads, the thread driving the read | `threads(n)` |
| I/O | a virtual thread per request or footer read, which does nothing but the read; for an S3 file, the transfer runs on the `HttpClient`'s own threads ([Thread inventory](#thread-inventory)) | no budget per context; a read's fetches ahead of its consumer are bounded by F and the context's read-ahead buffer, and a multi-file read opens up to `maxFilesAhead` files ahead within both |
| The read's state | one lock per read, held by whichever thread applies a result, for bookkeeping only | one holder at a time |
| The read loop and the consumer's own work | the caller's thread | the caller |

A thread of the pool never waits for work queued on the pool, nor for a request to a file whose bytes are not in memory; it waits only for work another thread is running (the read's lock, which is held for bookkeeping, and a cell's lock while another job allocates its arrays), and a writer's append worker waits a bounded time for the caller ([Writes](#writes)). Code on the pool is a state machine over what is present: where it needs bytes or a result that is not present, it returns the need, and the read runs it again once the need is met. Only I/O waits, on a virtual thread that does nothing but the read.

The control flow a read runs on fetched bytes is a state machine wherever Parquet makes it sequential. A row group's pruning reads follow one another (a Bloom filter or dictionary page whose extent the footer omits is read header first), so pruning that waited for them would hold a thread for the read's whole round trips: its read step reads the bytes the read holds and records the ranges it lacks (`Parsed`), and the read fetches them and runs the step again once they have arrived, before one evaluation decides. A chunk without an OffsetIndex is scanned header by header as its ranges arrive, a scan job at a time, each stopping at the first byte not present. What runs next is decided by the read's scheduler alone ([READ_PIPELINE.md](READ_PIPELINE.md#scheduling)).

## Thread inventory

| Thread | Count | Lifetime | Does |
|---|---|---|---|
| CPU job (pool) | at most twice the decode threads per read, queued or running | one job | On the `HardwoodContext` pool, at the tail of its queue, in the order the read's scheduler starts them ([READ_PIPELINE.md](READ_PIPELINE.md#scheduling)): a plan job parses one footer, prunes one unit by its Bloom filters and dictionaries, or plans one unit's pages and ranges; a decode job parses its page's header, charges R for its task where that exceeds the retained size, and decodes one page, into its cells for a flat column, completing the cells it fills last, or for a column decoded through levels its levels into scratch the page owns, which it measures, or parses one dictionary page; a scan job walks a chunk's headers through the bytes present; a fill job fills a sealed nested cell or completes a sealed flat cell. Each parses, scans and decodes in place, so its CPU is the pool's |
| Applying results | whichever thread ends a job or calls back into the read | one batch of results | Under the read's lock: applies a job's result (placing pages, marking cells completed, publishing), asks the scheduler what starts next, and dispatches it once the lock is let go of. On a read of several decode threads, a thread that finds the lock held queues its result for the holder ([READ_PIPELINE.md](READ_PIPELINE.md#scheduling)). The consumer's room listener, a release of the read-ahead buffer and another read's footer load completing call back into the read the same way |
| Dictionary task | one per dictionary page a thread off the pool decodes | one page | Parses a dictionary page on the `HardwoodContext` pool for a caller off it, such as the CLI, which waits for it (`HardwoodContextImpl.decode`). A job of a read decodes in place |
| Read (virtual) | as triggered | one request | On a virtual thread of its own, named `hardwood-io`, from the context's I/O executor (`HardwoodContextImpl.ioExecutor`), each read of a file whose bytes are not in memory: the read's fetches of data, dictionaries, page-index windows and Bloom filters, and its footer reads, each of which opens a file and reads its tail and footer, or checks a supplied footer against the file. It parses nothing: a plan job parses what a fetch or a footer read delivered. One exception: a `MetadataSource` that has to read a footer from the file parses it on the footer read's virtual thread. The read counts every one of them until its result is applied, and its close waits for them. A footer a caller off the read asks for loads on the caller's thread |
| HTTP client | the `HttpClient`'s selector thread and its executor's threads, per `S3Source` | the source's client | For a file of `hardwood-s3`, carries each request's transfer: reads and writes the socket, encrypts and decrypts TLS, and copies a range body into its direct buffer as it arrives (`RangeBodyHandler`, [S3_STORAGE.md](S3_STORAGE.md#range-reads)). The read's virtual thread waits in `HttpClient.send` until the body is received. The checks that fail a stalled body run on the thread of the JDK's shared `CompletableFuture` delay scheduler (`IdleBoundSubscriber`, [S3_STORAGE.md](S3_STORAGE.md#errors-and-retries)); each is a flag test, and the one that times a body out cancels its subscription. These threads belong to the client, not the context: their work is outside `threads(n)`, and a caller-supplied client runs it on the executor the caller gave it |
| Consumer | the caller's thread | caller-managed | Polls every column's exchange and reads the batches; its take runs the column's room listener, which publishes the batches that waited for room. Asks the questions a reader asks before the columns start, which metadata answers |

Decode runs only on the context's fixed platform-thread pool (`HardwoodContext.create(n)`, default one thread per processor), which every reader sharing the context submits to; a context of zero threads has none, and runs each read on the threads using it ([A context of zero threads](#a-context-of-zero-threads)). The pool size is the bound on decode parallelism. Decode code, a cell's completion included, takes a set of the context's `DecodeBuffers` as a parameter, and only a task of the pool, or on a context of zero threads the thread driving a read, is handed one, so other code cannot call it; a thread off the pool of a context that has one hands a page it needs decoded to the pool and waits ([VALUE_DECODE.md](VALUE_DECODE.md#decode-buffers)). Decode is CPU-bound and runs as one job per page, so it stays off the virtual-thread carriers, which every virtual thread in the process shares, and runs on a pool the caller sizes. A chunk's scan runs on the same pool, as scan jobs, each of which returns at the first header whose bytes are not present, so a scan waiting for bytes holds no thread. The reads are virtual threads on the JVM's default scheduler, which spend their time blocked on I/O and do nothing else.

## Invariants

1. **No read or write hands work to the JVM's common `ForkJoinPool`.** The common pool is sized for CPU work and shared with the application, so a read that blocked there would hold one of the application's threads. A read's CPU work runs on the context's pool or, on a context of zero threads, on the threads driving the read; a writer's on the pool and the caller. Untested.

2. **CPU work that grows with the data runs on the pool.** Parsing a footer after the first file's, pruning a row group by its statistics, Bloom filters and dictionaries, planning a unit's pages from its offset index, scanning headers and decoding pages are plan, scan and decode jobs ([Thread inventory](#thread-inventory)). A thread off the pool that needs such work hands it to the pool and waits, ahead of the queued read-ahead (`HardwoodContextImpl.compute`, `HardwoodContextImpl.decode`). A virtual thread does I/O only, so the pool's size bounds a read's CPU, and the virtual threads waiting on I/O find a carrier free. The first file's footer is parsed on the thread that opens the reader, which the caller owns. Applying a job's result runs on the thread that ended the job or called back, and does bookkeeping only. Tests: `MetadataParseThreadTest`, `HardwoodContextDecodeTest`.

3. **A job never waits for I/O.** A decode starts only once every range holding its page's bytes has arrived, and a scan or a pruning step reads the bytes present and stops, or records what it lacks, at the first byte that is not ([FETCH_PLANNING.md](FETCH_PLANNING.md#requests)). A file whose bytes are in memory is sliced in place on whichever thread asks; every other file is read on a virtual thread. A footer another read or a caller loads, and a charge R has no room for, are waited for with a callback into the read, not by a job. R's release runs the waiters of every read on the context on the releasing thread, so a read releases nothing to R while it holds its lock. Tests: `ReadYieldTest`, `PoolWaitTest`, `FileMetadataCacheTest`.

4. **Only reads do I/O.** Every `InputFile` access during a read happens on a read's virtual thread, on the thread that slices an in-memory file, or on a caller off the read (the first footer, a later footer a caller loads); decodes and scans work on fetched bytes ([FETCH_PLANNING.md](FETCH_PLANNING.md#pages)), and applying results and publishing touch no file. They parse no page header of a file in memory either, so a memory-mapped page's first touch does not happen under the read's lock through a header: a decode job parses its page's header on its own thread ([VALUE_DECODE.md](VALUE_DECODE.md#page-headers)). Untested: no test observes which thread first reads a mapped page. Closing a read interrupts no thread: interrupting a thread inside a `FileChannel` operation closes the channel for every reader sharing it ([INPUT_FILES.md](INPUT_FILES.md#contract)). A change that interrupts a thread running a read's job, or gives a decode file access, breaks that.

5. **A task of the pool never waits for work queued on the pool.** A pool of n threads whose n threads each wait for a task queued behind them stops. A read's jobs therefore wait for no other job: the read counts its jobs, holding no thread, and runs what depends on a result once it is applied. On a thread of the pool, `HardwoodContextImpl.decode` and `compute` run in place, and a read is never built on a thread of the context it reads with: `PreparedRead` refuses it with `IllegalStateException` (`HardwoodContextImpl.requireOffPool`). Tests: `MetadataParseThreadTest`, `HardwoodContextDecodeTest`, `FileMetadataCacheTest`, `PoolWaitTest`; a wait on queued work outside the decode and compute paths is untested.

6. **No monitor is held across a wait.** The reads are virtual threads, and so may be the calling thread, and on JDK 21 a virtual thread that blocks inside `synchronized`, or waiting to enter it, holds its carrier. A thread that holds a monitor while it waits for I/O or for another virtual thread could leave the threads it waits for no carrier to run on. Every lock a read takes that a virtual thread may wait on is therefore a `ReentrantLock` (the read's own, `RangeBackedInputFile`'s). A `synchronized` block around a fetch, or around a wait for another virtual thread, breaks that. Untested: the build runs on a JDK whose virtual threads do not pin on monitors.

7. **Every wait has a waker.** Each wait is ended by a result applied under the read's lock, followed by the scheduler's start of what it made possible:
   - a decode or a scan waiting for a range, by the range's arrival or final failure;
   - a charge R had no room for, by R's next release;
   - a footer another load reads, by that load's completion;
   - a decode held by the look-ahead, by the consumer's first unpublished row moving;
   - the consumer's poll, by a publish, the end of the column's stream, or the read's failure;
   - the read's close, by the end of its last job in flight (`ReadTasks.signal`).

   A job's count ends only once its result is applied, so a read found idle has published every column's failure or end. The end of a stream and a close that drains an exchange each leave an element in the exchange's queue, so a consumer still waiting takes one (`BatchExchange`). A reader's close is claimed by one thread, and a closer on another thread, such as the parent's, waits until the claimed close has completed (`CloseClaim`). Every waiting thread also looks again after a bounded time, which an abandoned read (invariant 9) and the consumer's progress check (invariant 10) rely on. A change that alters a wait's condition without such a waker stalls the read, which then fails (invariant 10) rather than waiting forever. Tests: `ReaderCloseMidReadTest`, `ReaderEndOfStreamTest`, `BatchExchangeTest`, `BatchExchangeRowLimitTest`, `ZeroThreadContextTest`, `ReadYieldTest`.

8. **A context's pool runs its tasks in arrival order, apart from the work a thread waits for.** A decode or `compute` a thread off the pool blocks on goes to the head of the queue (`DecodeExecutor`); every other task, a read's jobs among them, runs in the order it arrived, which is the order its scheduler started them in. The pool has one queue for every read and writer on the context, so a small read beside a full scan waits behind the scan's read-ahead. A read that needs a latency of its own beside other reads uses a context of its own, and the operating system shares the cores between the contexts' pools; an engine that reads splits in parallel on threads of its own uses a context of zero threads. The pool is the context's own: a caller-supplied executor is not supported, since a read waits for pool work, and reads issued from tasks of a bounded executor would starve it. Tests: `HardwoodContextDecodeTest`.

9. **A read whose bookkeeping fails ends with the failure.** Applying a job's result can throw, as reporting a failure does when the heap is exhausted; the result is then lost, and the read's job count never balances, so neither the consumer's wait nor the close of invariant 7 would end. The read is abandoned instead (`ReadDriver.submitOrAbandon`): its consumer raises the failure at its next call, its close returns without waiting for its jobs, and the throw reaches neither the pool nor another read whose thread applied the result. Abandoning allocates nothing, as it runs where an allocation has just failed; waking the threads waiting on the read may fail to allocate, so every wait on a read looks again after a bounded time. Abandoning surfaces the error and nothing more: after an `OutOfMemoryError` the JVM's state cannot be trusted, so the read's context and its accounting are not kept usable. Tests: `HeapExhaustionTest`, `ReadDriverTest`, `ReadTasksTest`, `BatchExchangeTest`.

10. **A read either progresses or fails.** A consumer waiting without a batch asks the read, under its lock, whether it can still progress (`ReadDriver.checkProgress`): on a pool after each bounded wait, on a context of zero threads each time no job of the read is queued or in flight. The read is stalled where the consumer still waits, no job of the read is in flight and no result is queued, starting jobs at the consumer's position starts nothing, and the read waits on nothing another read may release: room in R, or a footer another read loads. Nothing could then wake it, and it is abandoned (invariant 9) with an `IllegalStateException` naming the consumer's need, the look-ahead's reach, and the lowest pending job with the bound that refuses it. Where the check's own reconcile publishes the consumer's batch, or its start starts a job, no event tried work that was ready: a lost wake-up, which fails the read as well, so that the check never stands in for a missing waker. A check that throws, as its reconcile does where the heap is exhausted, abandons the read with the throw (invariant 9). The bounded wait decides only when the check runs, not whether a read fails: a slow fetch is a job in flight, so it never counts as a stall. A release of R on its way to the read counts as its waker: the read waits for room until a poll of its scheduler under its lock follows the release (`JobScheduler.waitingForRoom`), and a footer load another read ends until its end is applied under the lock. The check is per read: reads of one context that each wait on room another holds are not detected. Tests: `ReadDriverTest`, `BatchExchangeTest`, `ZeroThreadContextTest`.

## A context of zero threads

`HardwoodContext.create(0)` and `builder().threads(0)` create a context without a pool. Each read on it keeps its CPU jobs in a queue of its own (`ReadQueue`), created by its `ReadEngine`. The read's driver hands its CPU jobs to the queue where it would hand them to the pool, and the queue runs its jobs in the order the read's scheduler starts them. Every queue item is one the pool would run, so nothing of the read changes but the thread: placement, cells, fills, publishing, the order of the jobs and the bounds run as [READ_PIPELINE.md](READ_PIPELINE.md#scheduling) describes, the thread driving the read counting as one decode thread. The read's requests and footer reads still run on virtual threads.

The threads using the read run the queue. A poll that finds no batch (`BatchExchange.poll`) runs the item at the head and looks again; the read's close runs it while it waits. A thread that finds the queue empty parks until the read signals (`ReadTasks`), which every item queued, the end of its last job in flight and every publish, finish or failure of its exchanges does, or for at most a bounded time ([invariant 9](#invariants)). `BatchWait` spans the park, which waits for a read in flight. The read counts every job it emitted, its reads included, until the job's result is applied. A poll that finds no batch and no job of the read queued or in flight asks the read whether it can still progress, which fails a stalled read ([invariant 10](#invariants)), and otherwise parks for at most the bounded time before it asks again: the read then waits on another read.

`compute` and `decode` run in place on any thread, and `requireOffPool` never fails. **Invariant: on a context of zero threads no virtual thread a read starts runs `compute` or `decode`.** A read's virtual threads read and parse nothing; its footer parses are plan jobs of its queue. A caller that drives a read from a virtual thread of its own decodes on it, holding its carrier for each decode. A read of files in memory starts no thread: its requests are slices of the files, and its footers are read in place by their parse. A read of files not in memory keeps its fetches and footer reads ahead of its consumer as on a pool. A writer on such a context appends and encodes on the calling thread ([WRITER.md](WRITER.md#threading)). `HardwoodContext.executor()` throws `UnsupportedOperationException`.

The `zero-threads` Maven profile runs the core test suite a second time on contexts of zero threads, through the internal `hardwood.internal.zeroThreads` property, minus the tests tagged `pool`, which pin how work spreads over a pool's threads or rely on a read's work running while no thread drives it; it runs on demand, for changes to how a read or a write is driven. Tests: `ZeroThreadContextTest`.

## Writes

A writer runs on the same pool and the caller's thread: each slice of a batch is appended one column per task, and at flush the column chunks are encoded and compressed one per task, with the caller claiming work too ([WRITER.md](WRITER.md#threading)). A writer's task never waits for a task queued on the pool: a chunk's thread waits only for a page body a worker has claimed, and an append worker waits between slices for the caller, spinning and then parked, for a bounded time before it returns its pool thread. A writer and readers can therefore share a context. On a context of zero threads the caller appends and encodes alone.

## Boundaries

- **Reads off a read.** The reads a caller makes outside a read, the first file's footer, a later footer a caller loads and the CLI's direct reads, call the `InputFile` on the caller's thread, outside any read's count of jobs.
- **No bound on requests in flight, and needed bytes uncharged (#1687).** A context holds no budget on requests across its reads, and the fetch a read's consumer needs next, up to S, is charged to no budget.
- **Decode concurrency per read (#1573).** The pool size is the only bound on a read's concurrency of decodes within `DecodeBuffers.RETAINED_BYTES`, and a consumer-bound read uses as many threads as the look-ahead admits decodes for; larger decodes run beside the one need forces only within the read-ahead buffer ([READ_PIPELINE.md](READ_PIPELINE.md#scheduling)).
- **Pinning on JDK 21.** Invariant 6 exists because a virtual thread on JDK 21 holds its carrier while it blocks in or on a monitor. On a baseline of JDK 24 or later (JEP 491) virtual threads do not pin on monitors, and the rule and the `ReentrantLock`s it requires can go.
- **A warm page cache.** Invariant 3 holds for a memory-mapped file only while its pages are in the page cache: on a cold cache each first touch of a page faults on the thread making it ([INPUT_FILES.md](INPUT_FILES.md#local-files-memory-mapping)).
