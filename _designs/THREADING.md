# Threading

Describes which thread runs each piece of work a read or a write does on a `HardwoodContext`: the context's pool for CPU work, virtual threads for I/O and for a row group's planning, the caller's thread for the read loop, and a context of zero threads, whose reads run on the threads driving them. States the invariants that keep a pool thread from waiting and the context's thread count a bound on a read's CPU.

## Carriers

A read uses two resources of its context: CPU time and requests in flight. Each kind of work runs on the carrier that matches the resource it uses.

| Resource | Carrier | Bound |
|---|---|---|
| CPU, control steps included | the context's pool of `n` platform threads; on a context of zero threads, the thread driving the read | `threads(n)` |
| I/O | a virtual thread per request, which does nothing but the request; for an S3 file, the transfer runs on the `HttpClient`'s own threads ([Thread inventory](#thread-inventory)) | no budget per context; read-ahead goes one unit ahead per chunk handle, region and row group, and a multi-file read opens up to `maxFilesAhead` files ahead within the context's read-ahead buffer |
| Planning a row group | a virtual thread per work item, which waits for the planning's requests and hands its CPU work to the pool; for a read whose files are all in memory, or on a context of zero threads, the fetch step that reaches the work item (`RowGroupIterator.PlanningMode`) | one row group ahead of the read |
| The read loop and the consumer's own work | the caller's thread | the caller |

A thread of the pool never waits for work queued on the pool, nor for a request to a file whose bytes are not in memory; it waits only for work another thread is running, and a writer's append worker waits a bounded time for the caller ([Writes](#writes)). Code on the pool is a state machine over what is present: where it needs bytes or a result that is not present, it returns the need, and the step that runs it yields on the need and is queued again once the need is met. Code that waits runs on a virtual thread and hands its CPU work to the pool (`HardwoodContextImpl.compute`), where the context bounds it.

How often a piece of control flow runs decides which of the two it is. The walk over a column's pages runs once per page, where a hand-off to a virtual thread and back would cost on every page, so it is a state machine whose steps run on the pool. A row group is planned once, mostly waiting for requests that follow one another (the next file's footer, the row group's Bloom filters, dictionaries leaf by leaf, its index window, the mask probe), so its planning is plain blocking code on a virtual thread, and a step that reaches the row group before its plans are ready yields on them.

## Thread inventory

| Thread | Count | Lifetime | Does |
|---|---|---|---|
| Fetch step (pool) | at most one queued or running per decoded column | until its column's queue is full or its fetch ends | The column's fetcher. On the `HardwoodContext` pool, at the head of its queue: advances the `PageSource`, which takes each work item's planning and walks its fetch plan's pages (`PageWalk`); decodes each chunk's dictionary page in place; places a flat column's pages into cells; queues pages for the scheduler (`ScheduledColumn.runFetchStep`). A change that makes room in the column's queue queues its next step. Where the next page needs bytes that are not present, the step issues their read as demand and yields on it, holding the column's claim and its count of tasks, and the read's completion queues the next step; where the next work item is still being planned, it yields on the planning likewise; where a dictionary page's parse is not admitted beside the read's other tasks (`WorkingSet.admitTask`), it yields until a task of the read ends |
| Page task | up to the read-ahead bounds per read | one page | Decodes one page on the `HardwoodContext` pool: into its cells for a flat column; for a nested column, levels and ids into scratch the page owns, which it measures and places, filling the cells its placement seals. Completes and publishes the cells it finishes; a `SealedFillTask` fills or completes the cells the fetch steps sealed |
| Dictionary task | one per dictionary page a thread off the pool decodes | one page | Parses a dictionary page on the `HardwoodContext` pool for the caller's dictionary probe, which waits for it (`HardwoodContextImpl.decode`). A fetch step or a planning task decodes in place |
| Planning (virtual) | one per work item of a read whose files are not all in memory | one work item | On a virtual thread of the context's I/O executor (`WorkItemPlanning`): plans a work item once a column reaches it, the next file's footer and statistics when the work list needs the next file, then the row group's Bloom filters, dictionaries, index window, page filter, mask probe and fetch plans, waiting for each read it makes. Its parsing, scans and plan building run on the pool (`compute`). The next row group is planned ahead of its read on the virtual thread that read its index window, which then starts the read of its first chunk. The files a read opens ahead are planned in order, once their footers are read, on a virtual thread of their own (`RowGroupIterator.planFilesAhead`), which waits for the planning lock. The iterator's `PrefetchTasks` tracks it |
| Planning task (pool) | one per row group of a read whose files are all in memory, once its index window is read | one row group | At the tail of the `HardwoodContext` pool: plans the next row group ahead of its read (its page filter, its fetch plans, under a filter its dictionaries) and starts the read of its first chunk. The iterator's `PrefetchTasks` for planning tracks it |
| Read (virtual) | as triggered | one request | On a virtual thread of its own, named `hardwood-io`, from the context's I/O executor (`HardwoodContextImpl.ioExecutor`), each read of a file whose bytes are not in memory (`RangeRead`): the chunks and regions a fetch step's walk needs, which it yields on (demand), and the speculative reads: a later file's footer read (its bytes, or a supplied footer checked against the file), the span of a file opened ahead, the next row group's index window and Bloom filters, its first chunk, one-ahead chunk and region prefetches. It parses nothing: the load that takes a footer read parses it, the read of an index window is followed by the row group's planning, and a completed chunk read queues the step that waits for it. The iterator's `PrefetchTasks` tracks all but the footer reads, which the `FileMetadataCache` tracks. A footer no prefetch has read loads on the thread that asks for it |
| HTTP client | the `HttpClient`'s selector thread and its executor's threads, per `S3Source` | the source's client | For a file of `hardwood-s3`, carries each request's transfer: reads and writes the socket, encrypts and decrypts TLS, and copies a range body into its direct buffer as it arrives (`RangeBodyHandler`, [S3_STORAGE.md](S3_STORAGE.md#range-reads)). The read's virtual thread waits in `HttpClient.send` until the body is received. These threads belong to the client, not the context: their work is outside `threads(n)`, and a caller-supplied client runs it on the executor the caller gave it |
| Consumer | the caller's thread | caller-managed | Polls every column's exchange and reads the batches; publishes the batches that waited for room |

Decode runs only on the context's fixed platform-thread pool (`HardwoodContext.create(n)`, default one thread per processor), which every reader sharing the context submits to; a context of zero threads has none, and runs each read on the threads using it ([A context of zero threads](#a-context-of-zero-threads)). The pool size is the bound on decode parallelism. Decode code, a cell's completion included, takes a set of the context's `DecodeBuffers` as a parameter, and only a task of the pool, or on a context of zero threads the thread driving a read, is handed one, so other code cannot call it; a thread off the pool of a context that has one hands a page it needs decoded to the pool and waits ([VALUE_DECODE.md](VALUE_DECODE.md#decode-buffers)). Decode is CPU-bound and runs as one task per page, so it stays off the virtual-thread carriers, which every virtual thread in the process shares, and runs on a pool the caller sizes. A column's fetcher runs on the same pool, as fetch steps: a step walks page headers, plans and places, and returns once its column's queue is full or its next page needs a read under way, so a fetch stopped for room or for bytes holds no thread. The reads are virtual threads on the JVM's default scheduler, which spend their time blocked on I/O and do nothing else. No read work runs on the JVM's common `ForkJoinPool`.

## Invariants

1. **No read or write hands work to the JVM's common `ForkJoinPool`.** A read's CPU work runs on the context's pool or, on a context of zero threads, on the threads driving the read; its waits for I/O run on virtual threads of the context's I/O executor; a writer's work runs on the pool and the caller. The common pool is sized for CPU work and shared with the application, so a blocking read there would hold one of its threads. Untested.

2. **CPU work on fetched bytes runs on the pool.** Besides decoding pages, a read parses and scans what it fetches as it goes: the footer of every file after the first, about a microsecond per column chunk; a file's row groups, which a filter prunes by their statistics; the column indexes a filter evaluates and the offset indexes each row group's fetch plans are built from, a fraction of a microsecond per column and page; and a row group's dictionary, which a filter scans for its literals, every entry once per leaf the dictionary can decide, up to milliseconds for a large dictionary (`RowGroupDictionaryFilterSource.absent`). A fetch step or a planning task on the pool runs that work in place (`HardwoodContextImpl.compute`); the calling thread, which plans the first row groups, and a virtual thread planning a work item hand it to the pool, which runs it ahead of the queued read-ahead, as a decode the thread waits for. A row group's page filter and its fetch plans are one hand-off each, whatever the column count, a dictionary check one per leaf. A virtual thread does I/O, or plans a work item and waits for its reads, and runs no work that grows with the data, so the pool's size bounds a read's CPU, and the virtual threads that wait on I/O find a carrier free. The rule holds for work that looks small: the cost of a hand-off, tens of microseconds on an idle pool and up to the length of a page task on a busy one, is accepted as the price of the bound. One exception: a row group's Bloom filter probes hash the filter's literals on the thread that plans the row group, a planning's virtual thread or the caller, a few microseconds per literal, interleaved with the reads of filters whose length the footer does not give. The first file's footer is parsed on the thread that opens the reader, which the caller owns. CPU work moved onto a virtual thread runs outside the threads the caller sized and holds a carrier for its length. Tests: `MetadataParseThreadTest`, `HardwoodContextDecodeTest`. Submission and publishing have no thread of their own and run on whichever thread triggers them ([READ_PIPELINE.md](READ_PIPELINE.md#scheduled-columns)).

3. **A fetch step never waits for I/O.** A column's walk takes a page's bytes from its chunk handles without waiting and without issuing a read (`ChunkHandle.poll`); where they are not present it returns them as a need (`ByteNeed`), and the step issues the read. A file whose bytes are in memory (`MappedInputFile`, `ByteBufferInputFile`) is sliced in place, on whichever thread asks, and is opened, and its footer read, by the load that first asks for it, a fetch step included ([FILE_METADATA.md](FILE_METADATA.md#per-file-metadata)); every other file is read on a virtual thread, and the step yields on the read ([FETCH_PLANNING.md](FETCH_PLANNING.md#chunk-handles-and-prefetch)). A read the step issues is demand. A work item of a read whose files are not all in memory is planned on a virtual thread (`WorkItemPlanning`), which waits for the planning's reads: the next file's footer, the row group's Bloom filters, dictionaries, index window and mask probe. A step that reaches the work item before its planning completes yields on it (`Need`), and the planning's completion queues the next step. A step that reaches a dictionary page larger than the retention size while another large task of the read runs and the context's read-ahead buffer has no room for it yields until a task of the read ends ([VALUE_DECODE.md](VALUE_DECODE.md#page-decode)); the task that ends runs the waiters of every read on the context, on its own thread, and each waiter only queues a step, submits its own read's pages, whose failure ends that read and does not leave the waiter, or opens its read's files ahead, which waits for no lock and releases nothing to the buffer while it holds its own. A read whose files are all in memory waits for no read, so the step that reaches a work item plans it. Before the read starts, the caller plans the first row groups on its own thread. Planning stays blocking code where the walk is a state machine because it runs once per row group, where a hand-off to a virtual thread costs nothing measurable, and the walk once per page. Tests: `FetchStepYieldTest`, which checks that every read of a column's pages ran on a virtual thread; `PoolWaitTest`, which holds back every read of a file not in memory until the pool has gone idle; `WorkItemPlanningTest`.

4. **Only reads and plannings do I/O.** Every `InputFile` access during a read happens on a read's or a work item's planning's virtual thread, on the thread that slices an in-memory file or plans one, or on the caller before the read starts; page tasks work on bytes the fetch step resolved ([FETCH_PLANNING.md](FETCH_PLANNING.md#fetch-plans)), and submission and publishing touch no file. Closing a column interrupts no thread: interrupting a thread inside a `FileChannel` operation closes the channel for every reader sharing it ([INPUT_FILES.md](INPUT_FILES.md#contract)). A change that interrupts a thread running a fetch step, or gives a page task file access, breaks that.

5. **A task of the pool never waits for work queued on the pool.** A fetch step and a planning task run on the pool, and a pool of n threads whose n threads each wait for a task queued behind them stops. On a thread of the pool, `HardwoodContextImpl.decode` and `compute` run in place. Every speculative task a fetch step may wait for does no CPU work queued on the pool: a footer read only reads, and the load that takes it parses; the next row group's planning runs on a virtual thread, which no step waits for, or, for a read whose files are all in memory, as a task of its own, and a fetch step that reaches the row group while that task plans it waits for a running thread (`OnceCache`), and plans it itself before the task has started. A footer load that a thread off the pool runs, such as the caller asking for a later file's metadata, hands its parse to the pool as a task a thread of the pool waiting for that load runs in place unless a thread has started it (`FileMetadataCache.Load`). A wait for a queued task on a thread of the pool breaks that. Tests: `MetadataParseThreadTest`, `HardwoodContextDecodeTest`, `NestedFillThreadTest`, `FileMetadataCacheTest`; a wait on queued work outside the decode, compute and footer-load paths is untested.

6. **No monitor is held across a wait.** The speculative reads are virtual threads, and so may be the calling thread, and on JDK 21 a virtual thread that blocks inside `synchronized`, or waiting to enter it, holds its carrier. A thread that holds a monitor while it waits for I/O or for another virtual thread could leave the threads it waits for no carrier to run on. Every lock a read takes across a fetch or a wait for another thread is therefore a `ReentrantLock` (the iterator's planning lock, a `ChunkHandle`'s, a `SharedRegion`'s, an `IndexWindow`'s, `LazyMaskCapability`'s, `RangeBackedInputFile`'s), and the per-row-group caches are `OnceCache`s, which hold no lock while they compute, where a `ConcurrentHashMap.computeIfAbsent` holds a monitor for the whole of its mapping function. A `synchronized` block around a fetch, or around a wait for another virtual thread, breaks that. Untested: the build runs on a JDK whose virtual threads do not pin on monitors.

7. **Speculative work never fails a read.** A failed plan or chunk prefetch leaves its plan or chunk unfetched, and the demand path repeats the work; a failed footer read fails the load that takes it, which the `FileMetadataCache` keeps, and the demand path rethrows it. Either way the failure is raised to a caller that is waiting for it. A failure no caller waits for is reported (`PrefetchTasks.report`): a failure of the file (an I/O failure, a malformed or unsupported file) is logged at `DEBUG`, any other `RuntimeException` at `WARNING`, and an `Error` is thrown by the close that waits for the work, the iterator's for a task and the `FileMetadataCache`'s for a footer read no load took, once the caches and the files are released. Work whose failure must surface stays off the speculative task: resolving the next work item, which validates the next file's schema, runs in the current work item's planning before the speculative task is started, and the iterator keeps a failure there for the demand path to rethrow. A work item's planning that fails is taken by every column that reaches the work item, and an `Error` it fails with that no column took is thrown by the iterator's close.

8. **Every wait is released by its waker.** A fetch stopped for room in its queue, a fetch step stopped on a read, which the read's completion queues again whether it succeeds or fails, a close's wait for the read's tasks, and the consumer's poll each re-check a monotone condition, and every change of that condition queues a fetch step, signals the read's waiting threads (`ReadTasks.signal`) or hands its queue an element. The end of a stream offers the exchange's end-of-stream sentinel after setting its flag, and draining a closed exchange leaves the sentinel in its queue, so a consumer still waiting when the offer found the queue full, or when a close on another thread drained it, takes an element. A change that alters a wait's condition without that signal leaves the thread parked, or the fetch stopped, forever. A column has at most one fetch step queued or running, which holds a claim; a change raises a flag before it tries the claim, and a step that stops for room releases the claim before it reads the flag, so a change either finds the claim free and queues a step or is seen by the step that holds it. Every wait is untimed. A column's close stops the read and waits until no fetch step or page task of the read is in flight, the last of which signals; a close counts itself as a task while it stops the read, so a reader and its parent closing one read on two threads both wait until the read is stopped and quiescent, and a closer of the reader waits until the claimed close has completed (`CloseClaim`). A task that ends its column, such as a fetch step the closed context refuses, publishes the column's failure or end before it stops being counted, since a poll on a context of zero threads that found the read idle first would report a stall. Tests: `ScheduledColumnCloseTest`, `ReaderCloseLatencyTest`, `ReaderEofLatencyTest`, `BatchExchangeTest`, `BatchExchangeRowLimitTest`, `ZeroThreadContextTest`.

9. **A context's pool runs its tasks in arrival order, apart from the work a thread waits for.** A column's fetch step, and a decode or `compute` a thread off the pool blocks on, go to the head of the queue (`DecodeExecutor`); every other task, page tasks and the planning of a read whose files are all in memory among them, runs in the order it arrived. The pool has one queue for every read and writer on the context, so a small read beside a full scan waits behind the scan's read-ahead. A read that needs a latency of its own beside other reads uses a context of its own, and the operating system shares the cores between the contexts' pools; an engine that reads splits in parallel on threads of its own uses a context of zero threads. The pool is the context's own: a caller-supplied executor is not supported, since a read waits for pool work, and reads issued from tasks of a bounded executor would starve it. Tests: `HardwoodContextDecodeTest`.

## A context of zero threads

`HardwoodContext.create(0)` and `builder().threads(0)` create a context without a pool. Each read on it keeps its fetch steps, page tasks and planning in a queue of its own (`ReadQueue`), created by its `RowGroupIterator` and shared with its `ReadScheduler`. The queue is the read's `ReadExecutor`, as the pool is on a context with one, and keeps the order the pool's queue gives: a fetch step at the head, a page task and planning at the tail. Every queue item is one the pool would run, so nothing of the read changes but the thread: placement, cells, fills, publishing, the scheduler's order and its cap run as [READ_PIPELINE.md](READ_PIPELINE.md#scheduled-columns) describes, the thread driving the read counting as one decode thread.

The threads using the read run the queue. A poll that finds no batch (`BatchExchange.drive`) runs the item at the head and looks again; a column's close and the close of the planning tasks run it while they wait for the read's work to end. A thread that finds the queue empty parks until the read signals (`ReadTasks`), which every item queued, every item ended, the last fetch step or page task of the read ending, and every publish, finish or failure of the read's exchanges does. `BatchWait` spans the park, which waits for a fetch step's read in flight; the reads planning makes block inside an item, and no `BatchWait` records them. The read counts its fetch steps and page tasks queued or running, a step yielded on a read or on a task's end among them (`ReadTasks`). A poll that finds no batch and none of them fails with an `IllegalStateException` instead of parking: nothing could publish a batch any more, which only a lost wake-up in Hardwood brings about.

`compute` and `decode` run in place on any thread, and `requireOffPool` never fails. **Invariant: on a context of zero threads no virtual thread a read starts runs `compute` or `decode`.** A caller that drives a read from a virtual thread of its own decodes on it, holding its carrier for each decode. A read plans each work item on the fetch step that reaches it, as a read of files in memory does with a pool, so planning runs on the consumer and waits for its reads there; the later file's footer a virtual thread reads is parsed by the load that takes it. A read of files in memory starts no thread: it does not prefetch the next footer or plan the next row group ahead, which on one thread would only reorder its work. A read of files not in memory keeps its speculative reads on virtual threads, and queues the next row group's planning at the tail of its queue once its index window is read, and the planning of the files it opens ahead once their footers are read. A writer on such a context appends and encodes on the calling thread ([WRITER.md](WRITER.md#threading)). `HardwoodContext.executor()` throws `UnsupportedOperationException`.

The `zero-threads` Maven profile runs the core test suite a second time on contexts of zero threads, through the internal `hardwood.internal.zeroThreads` property, minus the tests tagged `pool`, which pin how work spreads over a pool's threads or rely on a read's work running while no thread drives it; it runs on demand, for changes to how a read or a write is driven. Tests: `ZeroThreadContextTest`.

## Writes

A writer runs on the same pool and the caller's thread: each slice of a batch is appended one column per task, and at flush the column chunks are encoded and compressed one per task, with the caller claiming work too ([WRITER.md](WRITER.md#threading)). A writer's task never waits for a task queued on the pool: a chunk's thread waits only for a page body a worker has claimed, and an append worker waits between slices for the caller, spinning and then parked, for a bounded time before it returns its pool thread. A writer and readers can therefore share a context. On a context of zero threads the caller appends and encodes alone.

## Boundaries

- **One request entry for every read (#1264).** Every read a fetch step yields on goes through `RangeRead.start`. The reads of planning (footers, index windows, Bloom filters, dictionaries, the mask probe) call `InputFile.readRange` directly, on a planning's virtual thread or the caller, so no single place sees, or could bound, every request of a read.
- **No bound on requests or bytes in flight (#1264).** Read-ahead is one unit ahead at each level but one: the files a multi-file read opens ahead, which a count bounds per read and the context's read-ahead buffer in bytes. A context holds no budget on requests across its reads.
- **Decode concurrency per read (#1573).** The pool size is the only bound on a read's decode concurrency, and a consumer-bound read uses as many threads as the read-ahead cap admits pages for.
- **Pinning on JDK 21.** Invariant 6 exists because a virtual thread on JDK 21 holds its carrier while it blocks in or on a monitor. On a baseline of JDK 24 or later (JEP 491) virtual threads do not pin on monitors, and the rule, the `ReentrantLock`s it requires and the `OnceCache`s that replace `computeIfAbsent` can go.
