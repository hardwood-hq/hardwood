# Threading

Describes which thread runs each piece of work a read or a write does on a `HardwoodContext`: the context's pool for CPU work, a read's planning included, virtual threads for I/O, the caller's thread for the read loop, and a context of zero threads, whose reads run on the threads driving them. States the invariants that keep a pool thread from waiting and the context's thread count a bound on a read's CPU.

## Carriers

A read uses two resources of its context: CPU time and requests in flight. Each kind of work runs on the carrier that matches the resource it uses.

| Resource | Carrier | Bound |
|---|---|---|
| CPU: walk advances, planning, decodes, and applying their results | the context's pool of `n` platform threads; on a context of zero threads, the thread driving the read | `threads(n)` |
| I/O | a virtual thread per request or footer read, which does nothing but the read; for an S3 file, the transfer runs on the `HttpClient`'s own threads ([Thread inventory](#thread-inventory)) | no budget per context; a read's speculative data is bounded by F and the context's read-ahead buffer, and a multi-file read opens up to `maxFilesAhead` files ahead within that buffer |
| The read's state | one lock per read, held by whichever thread applies a result, for bookkeeping only | one holder at a time |
| The read loop and the consumer's own work | the caller's thread | the caller |

A thread of the pool never waits for work queued on the pool, nor for a request to a file whose bytes are not in memory; it waits only for work another thread is running (the read's lock, which is held for bookkeeping, and a cell's lock while another job allocates its arrays), and a writer's append worker waits a bounded time for the caller ([Writes](#writes)). Code on the pool is a state machine over what is present: where it needs bytes or a result that is not present, it returns the need, and the read runs it again once the need is met. Only I/O waits, on a virtual thread that does nothing but the read.

Both kinds of control flow a read runs on fetched bytes are state machines. The walk over a column's pages runs once per page, so a hand-off to another thread and back would cost on every page. A row group's planning runs once, but its reads follow one another (the next file's footer, the row group's Bloom filters, its dictionaries leaf by leaf, its index window, the mask probe), so a planner that waited for them would hold a thread for the read's whole round trips. Each of its parses reads the bytes the read holds and returns the range it lacks (`Parsed`), and the read demands that range and runs the stage again once it has arrived. What runs next is decided by the read's poll alone ([READ_PIPELINE.md](READ_PIPELINE.md#one-decision-point)).

## Thread inventory

| Thread | Count | Lifetime | Does |
|---|---|---|---|
| Walk advance (pool) | at most one queued or running per decoded column | one advance | On the `HardwoodContext` pool, at the head of its queue: advances the column's walk over its work item's fetch plan (`PageWalk`) up to the pages the column may hold, and decodes each chunk's dictionary page in place. Where the next page needs bytes that are not present, or a dictionary page's parse is not admitted beside the read's other tasks (`WorkingSet.admit`), it stops and returns the need; the read demands the request, or waits for a task of the read to end, and runs the column's walk again once the need is met |
| Decode (pool) | up to twice the decode threads per read, plus the jobs that finish sealed cells | one page, or one column's sealed cells | On the `HardwoodContext` pool, at the tail of its queue: decodes one page, into its cells for a flat column, completing the cells it fills last; for a column decoded through levels, levels and ids into scratch the page owns, which it measures. Another decode job completes a flat column's cells sealed after their last fill, or fills the cells a placement of a column decoded through levels sealed |
| Planning (pool) | at most one queued or running per read | one stage | On the `HardwoodContext` pool, at the tail of its queue: lists one file into the work list, takes one work item through one stage (Bloom filters and dictionaries, page index and page filter, mask probe, fetch plans and batches), or parses one footer. Where a stage lacks bytes it returns the planning request holding them, which the read demands. It parses, scans and builds plans in place, so its CPU is the pool's ([FETCH_PLANNING.md](FETCH_PLANNING.md#planning-ahead)) |
| Applying results | whichever thread ends a job or calls back into the read | one batch of results | Under the read's lock: applies a job's result (placing a flat column's pages, placing a column's measured pages, marking cells completed, publishing), polls, and dispatches what the poll emitted once the lock is let go of. On a read of several decode threads, a thread that finds the lock held queues its result for the holder ([READ_PIPELINE.md](READ_PIPELINE.md#one-decision-point)). The consumer's room listener, a release of the read-ahead buffer, another read's footer load completing and a need met call back into the read the same way |
| Dictionary task | one per dictionary page a thread off the pool decodes | one page | Parses a dictionary page on the `HardwoodContext` pool for a caller off it, such as the CLI, which waits for it (`HardwoodContextImpl.decode`). A walk advance or a planning stage decodes in place |
| Read (virtual) | as triggered | one request | On a virtual thread of its own, named `hardwood-io`, from the context's I/O executor (`HardwoodContextImpl.ioExecutor`), each read of a file whose bytes are not in memory: the read's data requests, demanded by a walk or started ahead of it, its planning requests (index windows, dictionaries, Bloom filters, probes), and its footer reads, each of which opens a file and reads its tail and footer, or checks a supplied footer against the file. It parses nothing: a planning job parses what a planning request or a footer read delivered. One exception: a `MetadataSource` that has to read a footer from the file parses it on the footer read's virtual thread. The read counts every one of them until its result is applied, and its close waits for them. A footer a caller off the read asks for loads on the caller's thread |
| HTTP client | the `HttpClient`'s selector thread and its executor's threads, per `S3Source` | the source's client | For a file of `hardwood-s3`, carries each request's transfer: reads and writes the socket, encrypts and decrypts TLS, and copies a range body into its direct buffer as it arrives (`RangeBodyHandler`, [S3_STORAGE.md](S3_STORAGE.md#range-reads)). The read's virtual thread waits in `HttpClient.send` until the body is received. The checks that fail a stalled body run on the thread of the JDK's shared `CompletableFuture` delay scheduler (`IdleBoundSubscriber`, [S3_STORAGE.md](S3_STORAGE.md#errors-and-retries)); each is a flag test, and the one that times a body out cancels its subscription. These threads belong to the client, not the context: their work is outside `threads(n)`, and a caller-supplied client runs it on the executor the caller gave it |
| Consumer | the caller's thread | caller-managed | Polls every column's exchange and reads the batches; its take runs the column's room listener, which publishes the batches that waited for room. Asks the questions a reader asks before the columns start, and waits for the read's jobs to answer them |

Decode runs only on the context's fixed platform-thread pool (`HardwoodContext.create(n)`, default one thread per processor), which every reader sharing the context submits to; a context of zero threads has none, and runs each read on the threads using it ([A context of zero threads](#a-context-of-zero-threads)). The pool size is the bound on decode parallelism. Decode code, a cell's completion included, takes a set of the context's `DecodeBuffers` as a parameter, and only a task of the pool, or on a context of zero threads the thread driving a read, is handed one, so other code cannot call it; a thread off the pool of a context that has one hands a page it needs decoded to the pool and waits ([VALUE_DECODE.md](VALUE_DECODE.md#decode-buffers)). Decode is CPU-bound and runs as one job per page, so it stays off the virtual-thread carriers, which every virtual thread in the process shares, and runs on a pool the caller sizes. A column's walk runs on the same pool, as walk advances: an advance walks page headers and parses dictionaries, and returns once its column holds as many pages as it may or its next page needs a read under way, so a walk stopped for room or for bytes holds no thread. The reads are virtual threads on the JVM's default scheduler, which spend their time blocked on I/O and do nothing else. No read work runs on the JVM's common `ForkJoinPool`.

## Invariants

1. **No read or write hands work to the JVM's common `ForkJoinPool`.** A read's CPU work runs on the context's pool or, on a context of zero threads, on the threads driving the read; its waits for I/O run on virtual threads of the context's I/O executor; a writer's work runs on the pool and the caller. The common pool is sized for CPU work and shared with the application, so a blocking read there would hold one of its threads. Untested.

2. **CPU work on fetched bytes runs on the pool.** Besides decoding pages, a read parses and scans what it fetches as it goes: the footer of every file after the first, about a microsecond per column chunk; a file's row groups, which a filter prunes by their statistics; the Bloom filters a filter probes, hashing its literals; the column indexes a filter evaluates and the offset indexes each row group's fetch plans are built from, a fraction of a microsecond per column and page; and a row group's dictionary, which a filter scans for its literals, every entry once per leaf the dictionary can decide, up to milliseconds for a large dictionary (`RowGroupDictionaryFilterSource.absent`). The read's planning jobs do all of it, on the pool, in place. A thread off the pool that needs such work hands it to the pool and waits, ahead of the queued read-ahead, as for a decode: the load of a later file's footer that a caller asks for (`HardwoodContextImpl.compute`), and a dictionary page the CLI parses (`HardwoodContextImpl.decode`). A virtual thread does I/O and runs no work that grows with the data, so the pool's size bounds a read's CPU, and the virtual threads that wait on I/O find a carrier free. The first file's footer is parsed on the thread that opens the reader, which the caller owns. CPU work moved onto a virtual thread runs outside the threads the caller sized and holds a carrier for its length. Applying a job's result runs on the thread that ended the job or called back, and does bookkeeping only. Tests: `MetadataParseThreadTest`, `HardwoodContextDecodeTest`.

3. **A job never waits for I/O.** A column's walk takes a page's bytes from the read's requests without waiting and without issuing a read (`Section.poll`); where they are not present it returns the request as a need, and the read starts it. A file whose bytes are in memory (`MappedInputFile`, `ByteBufferInputFile`) is sliced in place, on whichever thread asks, and its footer is read in place by the job that parses it ([FILE_METADATA.md](FILE_METADATA.md#per-file-metadata)); every other file is read on a virtual thread, and the walk stops until the read has arrived ([FETCH_PLANNING.md](FETCH_PLANNING.md#requests)). A planning stage never waits either: where it lacks bytes (a window's Bloom filters or page index, a dictionary page, a probe) it returns the planning request holding them. A footer another read or a caller loads is waited for with a callback, which calls back into the read once the load completes (`ReadPlanning.whenFooterDone`). A walk that reaches a dictionary page larger than the retention size while another large task of the read runs and the context's read-ahead buffer has no room for it stops until a task of the read ends ([VALUE_DECODE.md](VALUE_DECODE.md#page-decode)); the task that ends runs the waiters of every read on the context, on its own thread, and each waiter only calls back into its own read; a read releases nothing to the buffer while it holds its lock. Before the read starts, a caller that asks a question of the read (`hasLiveWorkItem`, `firstRowGroupSkip`, `canFastSkipAllRowGroups`) waits, parked, while the read's jobs answer it. Tests: `ReadYieldTest`, which checks that every read of a column's pages ran on a virtual thread; `PoolWaitTest`, which holds back every read of a file not in memory until the pool has gone idle; `IndexWindowTest`, `FileMetadataCacheTest`.

4. **Only reads do I/O.** Every `InputFile` access during a read happens on a read's virtual thread, on the thread that slices an in-memory file, or on a caller off the read (the first footer, a later footer a caller loads); decodes work on bytes the walk resolved ([FETCH_PLANNING.md](FETCH_PLANNING.md#fetch-plans)), and applying results and publishing touch no file. Closing a read interrupts no thread: interrupting a thread inside a `FileChannel` operation closes the channel for every reader sharing it ([INPUT_FILES.md](INPUT_FILES.md#contract)). A change that interrupts a thread running a walk advance, or gives a decode file access, breaks that.

5. **A task of the pool never waits for work queued on the pool.** A read's jobs wait for no other job: the read waits for a result by counting its jobs, holding no thread, and runs what depends on it once it is applied. A pool of n threads whose n threads each wait for a task queued behind them stops. On a thread of the pool, `HardwoodContextImpl.decode` and `compute` run in place. A job that waits for the read's lock, on a read of one decode thread, waits for a holder that does bookkeeping and then lets it go. A wait for a queued task on a thread of the pool breaks that. Tests: `MetadataParseThreadTest`, `HardwoodContextDecodeTest`, `FileMetadataCacheTest`, `PoolWaitTest`; a wait on queued work outside the decode and compute paths is untested.

6. **No monitor is held across a wait.** The reads are virtual threads, and so may be the calling thread, and on JDK 21 a virtual thread that blocks inside `synchronized`, or waiting to enter it, holds its carrier. A thread that holds a monitor while it waits for I/O or for another virtual thread could leave the threads it waits for no carrier to run on. Every lock a read takes that a virtual thread may wait on is therefore a `ReentrantLock` (the read's own, `RangeBackedInputFile`'s). A `synchronized` block around a fetch, or around a wait for another virtual thread, breaks that. Untested: the build runs on a JDK whose virtual threads do not pin on monitors.

7. **Speculative work fails a read only where the read reaches it.** A data request read ahead of demand that fails with an exception is read once more, and only its second failure goes to the walks that reach it. A footer read ahead that fails with an exception is read once more; its final failure, or an `Error`, ends planning at the file it belongs to, and every column that reaches that file takes the same instance, so a file ahead that cannot be read fails the read only there and every row before it is returned first. A planning failure, a planning request's final failure among them, ends planning likewise at the work item it hit. A request whose read fails with an `Error`, data or planning, is not read again: a walk that reaches it, or that waits for it, ends its column with the `Error` behind the pages it took before it, and a planning stage that reaches it ends planning at its work item. An `Error` a footer read or a request read ahead failed with that the read never raised is thrown once, by the read's close. A read ahead of demand that fails with an exception, a footer's or a request's, is logged at `DEBUG` as it fails; the walk, the stage or the listing that reaches it reports it.

8. **Every wait is released by its waker.** The read waits on its own state, and each wait is ended by a result applied under its lock and followed by a poll: a walk stopped on a request by the request's arrival or final failure; a walk or stage stopped on another need by the need's callback; a decode the working set did not admit, or a request R had no room for, by the end of a task of the read or a release of R; a footer another load reads by that load's completion; a walk held at the cap by the read's first unpublished row moving. The consumer's poll, a close and a caller asking a question re-check a monotone condition, and every poll signals the read's waiting threads (`ReadTasks.signal`); a publish hands the exchange's queue an element. The end of a stream offers the exchange's end-of-stream sentinel after setting its flag, and draining a closed exchange leaves the sentinel in its queue, so a consumer still waiting when the offer found the queue full, or when a close on another thread drained it, takes an element. Every wait is untimed. A change that alters a wait's condition without that result leaves the read waiting; the stall check fails such a read instead of leaving its consumer waiting ([READ_PIPELINE.md](READ_PIPELINE.md#one-decision-point)). The read's close waits until every job it emitted has ended and its result is applied, the last of which signals; a reader's close is claimed by one thread, and a closer on another thread, such as the parent's, waits until the claimed close has completed (`CloseClaim`). A job's count ends only once its result is applied, so a job that ends its column, such as one the closed context refuses, has published the column's failure or end by the time a poll on a context of zero threads finds the read idle. Tests: `ReaderCloseMidReadTest`, `ReaderEndOfStreamTest`, `BatchExchangeTest`, `BatchExchangeRowLimitTest`, `ZeroThreadContextTest`, `ReadYieldTest`.

9. **A context's pool runs its tasks in arrival order, apart from the work a thread waits for.** A column's walk advance, and a decode or `compute` a thread off the pool blocks on, go to the head of the queue (`DecodeExecutor`); every other task, a read's decodes and planning among them, runs in the order it arrived. The pool has one queue for every read and writer on the context, so a small read beside a full scan waits behind the scan's read-ahead. A read that needs a latency of its own beside other reads uses a context of its own, and the operating system shares the cores between the contexts' pools; an engine that reads splits in parallel on threads of its own uses a context of zero threads. The pool is the context's own: a caller-supplied executor is not supported, since a read waits for pool work, and reads issued from tasks of a bounded executor would starve it. Tests: `HardwoodContextDecodeTest`.

## A context of zero threads

`HardwoodContext.create(0)` and `builder().threads(0)` create a context without a pool. Each read on it keeps its walk advances, decodes and planning jobs in a queue of its own (`ReadQueue`), created by its `RowGroupIterator`. The queue is the read's `ReadExecutor`, as the pool is on a context with one, and keeps the order the pool's queue gives: a walk advance at the head, a decode or a planning job at the tail. Every queue item is one the pool would run, so nothing of the read changes but the thread: placement, cells, fills, publishing, the order of the decodes and the cap run as [READ_PIPELINE.md](READ_PIPELINE.md#decoded-columns) describes, the thread driving the read counting as one decode thread. The read's requests and footer reads still run on virtual threads.

The threads using the read run the queue. A poll that finds no batch (`BatchExchange.poll`) runs the item at the head and looks again; the read's close and a caller asking a question before the columns start run it while they wait. A thread that finds the queue empty parks until the read signals (`ReadTasks`), which every item queued, every item ended, every poll of the read and every publish, finish or failure of its exchanges does. `BatchWait` spans the park, which waits for a read in flight. The read counts every job it emitted, its reads included, until the job's result is applied. A poll that finds no batch and no job of the read in flight fails with an `IllegalStateException` instead of parking: nothing could publish a batch any more, which only a lost wake-up in Hardwood brings about.

`compute` and `decode` run in place on any thread, and `requireOffPool` never fails. **Invariant: on a context of zero threads no virtual thread a read starts runs `compute` or `decode`.** A read's virtual threads read and parse nothing; its footer parses are planning jobs of its queue. A caller that drives a read from a virtual thread of its own decodes on it, holding its carrier for each decode. A read of files in memory starts no thread: its requests are slices of the files, and its footers are read in place by their parse. A read of files not in memory keeps its speculative reads, its footer reads and its planning ahead as on a pool. A writer on such a context appends and encodes on the calling thread ([WRITER.md](WRITER.md#threading)). `HardwoodContext.executor()` throws `UnsupportedOperationException`.

The `zero-threads` Maven profile runs the core test suite a second time on contexts of zero threads, through the internal `hardwood.internal.zeroThreads` property, minus the tests tagged `pool`, which pin how work spreads over a pool's threads or rely on a read's work running while no thread drives it; it runs on demand, for changes to how a read or a write is driven. Tests: `ZeroThreadContextTest`.

## Writes

A writer runs on the same pool and the caller's thread: each slice of a batch is appended one column per task, and at flush the column chunks are encoded and compressed one per task, with the caller claiming work too ([WRITER.md](WRITER.md#threading)). A writer's task never waits for a task queued on the pool: a chunk's thread waits only for a page body a worker has claimed, and an append worker waits between slices for the caller, spinning and then parked, for a bounded time before it returns its pool thread. A writer and readers can therefore share a context. On a context of zero threads the caller appends and encodes alone.

## Boundaries

- **Reads off a read.** The reads a caller makes outside a read, the first file's footer, a later footer a caller loads and the CLI's direct reads, call the `InputFile` on the caller's thread, outside any read's count of jobs.
- **No bound on requests in flight, and demand bytes uncharged (#1687).** A context holds no budget on requests across its reads, and a read's demanded and next-unit requests, each up to S, are charged to no budget.
- **Decode concurrency per read (#1573).** The pool size is the only bound on a read's decode concurrency, and a consumer-bound read uses as many threads as the read-ahead cap admits pages for.
- **Pinning on JDK 21.** Invariant 6 exists because a virtual thread on JDK 21 holds its carrier while it blocks in or on a monitor. On a baseline of JDK 24 or later (JEP 491) virtual threads do not pin on monitors, and the rule and the `ReentrantLock`s it requires can go.
- **A warm page cache.** A file in memory includes a mapped local file (`MappedInputFile`), whose slices a walk advance and a decode read directly. Invariant 3 holds for it only while its pages are in the page cache: on a cold cache each first touch of a page faults on a thread of the pool, or on a context of zero threads on the thread driving the read (#1661).
