# Threading

Describes which thread runs each piece of work a read or a write does on a `HardwoodContext`: the context's pool for CPU work, a read's planning included, virtual threads for I/O, the caller's thread for the read loop, and a context of zero threads, whose reads run on the threads driving them. States the invariants that keep a pool thread from waiting and the context's thread count a bound on a read's CPU.

## Carriers

A read uses two resources of its context: CPU time and requests in flight. Each kind of work runs on the carrier that matches the resource it uses.

| Resource | Carrier | Bound |
|---|---|---|
| CPU, control steps included | the context's pool of `n` platform threads; on a context of zero threads, the thread driving the read | `threads(n)` |
| I/O | a virtual thread per request, which does nothing but the request; for an S3 file, the transfer runs on the `HttpClient`'s own threads ([Thread inventory](#thread-inventory)) | no budget per context; a read's speculative data is bounded by F and the context's read-ahead buffer, and a multi-file read opens up to `maxFilesAhead` files ahead within that buffer |
| Planning | the read's planning chain, one step of the pool at a time, which yields on the requests it needs rather than waiting for them; on a context of zero threads, items of the read's queue | one chain per read; how far it plans ahead is in [FETCH_PLANNING.md](FETCH_PLANNING.md#planning-ahead) |
| The read loop and the consumer's own work | the caller's thread | the caller |

A thread of the pool never waits for work queued on the pool, nor for a request to a file whose bytes are not in memory; it waits only for work another thread is running, and a writer's append worker waits a bounded time for the caller ([Writes](#writes)). Code on the pool is a state machine over what is present: where it needs bytes or a result that is not present, it returns the need, and the step that runs it yields on the need and is queued again once the need is met. Only I/O waits, on a virtual thread that does nothing but the request.

Both kinds of control flow a read runs are state machines. The walk over a column's pages runs once per page, so a hand-off to another thread and back would cost on every page. A row group's planning runs once, but its reads follow one another (the next file's footer, the row group's Bloom filters, its dictionaries leaf by leaf, its index window, the mask probe), so a planner that waited for them would hold a thread for the read's whole round trips. Each of its parses reads the bytes the read holds and returns the range it lacks (`Parsed`), and the planning chain demands that range and yields, keeping its place.

## Thread inventory

| Thread | Count | Lifetime | Does |
|---|---|---|---|
| Fetch step (pool) | at most one queued or running per decoded column | until its column's queue is full or its fetch ends | The column's fetcher. On the `HardwoodContext` pool, at the head of its queue: advances the `PageSource`, which takes each work item's planning and walks its fetch plan's pages (`PageWalk`); decodes each chunk's dictionary page in place; places a flat column's pages into cells; queues pages for the scheduler (`ScheduledColumn.runFetchStep`). A change that makes room in the column's queue queues its next step. Where the next page needs bytes that are not present, the step issues their read as demand and yields on it, holding the column's claim and its count of tasks, and the read's completion queues the next step; where the next work item is still being planned, it yields on the planning likewise; where a dictionary page's parse is not admitted beside the read's other tasks (`WorkingSet.admitTask`), it yields until a task of the read ends |
| Page task | up to the read-ahead bounds per read | one page | Decodes one page on the `HardwoodContext` pool: into its cells for a flat column; for a nested column, levels and ids into scratch the page owns, which it measures and places, filling the cells its placement seals. Completes and publishes the cells it finishes; a `SealedFillTask` fills or completes the cells the fetch steps sealed |
| Dictionary task | one per dictionary page a thread off the pool decodes | one page | Parses a dictionary page on the `HardwoodContext` pool for a caller off it, such as the CLI, which waits for it (`HardwoodContextImpl.decode`). A fetch step or the planning chain decodes in place |
| Planning chain (pool) | at most one step queued or running per read | one step | The read's planner (`PlanningChain`), run under a claim: at the tail of the pool's queue while it plans ahead of the read, at its head while a column or a caller waits for it, and in place by a fetch step that needs a work item planned and finds it idle. Lists files into the work list from their footers, loading a footer in place once it has been read, and takes each work item through its stages in work-list order: Bloom filters and dictionaries, page index and page filter, mask probe, fetch plans and batches. Where a stage lacks bytes it demands the entry holding them and yields, keeping the claim, and the entry's completion queues it again. It parses, scans and builds plans in place, so its CPU is the pool's ([FETCH_PLANNING.md](FETCH_PLANNING.md#planning-ahead)) |
| Read (virtual) | as triggered | one request | On a virtual thread of its own, named `hardwood-io`, from the context's I/O executor (`HardwoodContextImpl.ioExecutor`), each read of a file whose bytes are not in memory: the entries of the read's fetch sequence (`RangeRead`), data a fetch step's walk yields on (demand) or the sequence starts ahead of it, and the planning entries the chain yields on (index windows, dictionaries, Bloom filters, probes); and the footer reads, each of which opens a file and reads its tail and footer, or checks a supplied footer against the file. It parses nothing: the planning chain parses what a planning entry or a footer read delivered, and a completed read queues the step or the chain that waits for it. One exception: a `MetadataSource` that has to read a footer from the file parses it on the footer read's virtual thread. The read's `PrefetchTasks` tracks every one of them, whose close waits for them. A footer no read has read loads on the thread off the read that asks for it |
| HTTP client | the `HttpClient`'s selector thread and its executor's threads, per `S3Source` | the source's client | For a file of `hardwood-s3`, carries each request's transfer: reads and writes the socket, encrypts and decrypts TLS, and copies a range body into its direct buffer as it arrives (`RangeBodyHandler`, [S3_STORAGE.md](S3_STORAGE.md#range-reads)). The read's virtual thread waits in `HttpClient.send` until the body is received. The checks that fail a stalled body run on the thread of the JDK's shared `CompletableFuture` delay scheduler (`IdleBoundSubscriber`, [S3_STORAGE.md](S3_STORAGE.md#errors-and-retries)); each is a flag test, and the one that times a body out cancels its subscription. These threads belong to the client, not the context: their work is outside `threads(n)`, and a caller-supplied client runs it on the executor the caller gave it |
| Consumer | the caller's thread | caller-managed | Polls every column's exchange and reads the batches; publishes the batches that waited for room |

Decode runs only on the context's fixed platform-thread pool (`HardwoodContext.create(n)`, default one thread per processor), which every reader sharing the context submits to; a context of zero threads has none, and runs each read on the threads using it ([A context of zero threads](#a-context-of-zero-threads)). The pool size is the bound on decode parallelism. Decode code, a cell's completion included, takes a set of the context's `DecodeBuffers` as a parameter, and only a task of the pool, or on a context of zero threads the thread driving a read, is handed one, so other code cannot call it; a thread off the pool of a context that has one hands a page it needs decoded to the pool and waits ([VALUE_DECODE.md](VALUE_DECODE.md#decode-buffers)). Decode is CPU-bound and runs as one task per page, so it stays off the virtual-thread carriers, which every virtual thread in the process shares, and runs on a pool the caller sizes. A column's fetcher runs on the same pool, as fetch steps: a step walks page headers, plans and places, and returns once its column's queue is full or its next page needs a read under way, so a fetch stopped for room or for bytes holds no thread. The reads are virtual threads on the JVM's default scheduler, which spend their time blocked on I/O and do nothing else. No read work runs on the JVM's common `ForkJoinPool`.

## Invariants

1. **No read or write hands work to the JVM's common `ForkJoinPool`.** A read's CPU work runs on the context's pool or, on a context of zero threads, on the threads driving the read; its waits for I/O run on virtual threads of the context's I/O executor; a writer's work runs on the pool and the caller. The common pool is sized for CPU work and shared with the application, so a blocking read there would hold one of its threads. Untested.

2. **CPU work on fetched bytes runs on the pool.** Besides decoding pages, a read parses and scans what it fetches as it goes: the footer of every file after the first, about a microsecond per column chunk; a file's row groups, which a filter prunes by their statistics; the Bloom filters a filter probes, hashing its literals; the column indexes a filter evaluates and the offset indexes each row group's fetch plans are built from, a fraction of a microsecond per column and page; and a row group's dictionary, which a filter scans for its literals, every entry once per leaf the dictionary can decide, up to milliseconds for a large dictionary (`RowGroupDictionaryFilterSource.absent`). The planning chain does all of it, on the pool, in place. A thread off the pool that needs such work hands it to the pool and waits, ahead of the queued read-ahead, as for a decode: the load of a later file's footer that a caller asks for (`HardwoodContextImpl.compute`), and a dictionary page the CLI parses (`HardwoodContextImpl.decode`). A virtual thread does I/O and runs no work that grows with the data, so the pool's size bounds a read's CPU, and the virtual threads that wait on I/O find a carrier free. The first file's footer is parsed on the thread that opens the reader, which the caller owns. CPU work moved onto a virtual thread runs outside the threads the caller sized and holds a carrier for its length. Tests: `MetadataParseThreadTest`, `HardwoodContextDecodeTest`, `DecodeThreadTest`. Submission and publishing have no thread of their own and run on whichever thread triggers them ([READ_PIPELINE.md](READ_PIPELINE.md#scheduled-columns)).

3. **A fetch step never waits for I/O.** A column's walk takes a page's bytes from the read's fetch-sequence entries without waiting and without issuing a read (`FetchSequence.Entry.poll`); where they are not present it returns the entry as a need (`ByteNeed`), and the step demands it. A file whose bytes are in memory (`MappedInputFile`, `ByteBufferInputFile`) is sliced in place, on whichever thread asks, and is opened, and its footer read, by the load that first asks for it, a fetch step included ([FILE_METADATA.md](FILE_METADATA.md#per-file-metadata)); every other file is read on a virtual thread, and the step yields on the read ([FETCH_PLANNING.md](FETCH_PLANNING.md#entries)). An entry the step issues is demanded. The planning chain never waits either: where a stage lacks bytes (the next file's footer, a window's Bloom filters or page index, a dictionary page, a probe) it demands the entry holding them, or yields on another thread's load of the footer, and lets its thread go. A step that reaches a work item the chain has not planned asks for it and yields on the chain's cursor (`PlanningChain.whenPlanned`), and the chain's publishing of the work item queues the next step; a step that finds the chain idle runs it in place, which for a read whose files are all in memory plans the work item on the step. A step that reaches a dictionary page larger than the retention size while another large task of the read runs and the context's read-ahead buffer has no room for it yields until a task of the read ends ([VALUE_DECODE.md](VALUE_DECODE.md#page-decode)); the task that ends runs the waiters of every read on the context, on its own thread, and each waiter only queues a step, submits its own read's pages, whose failure ends that read and does not leave the waiter, or starts its read's speculative entries and footers; the last takes its own read's lock only briefly and release nothing to the buffer while they hold it. Before the read starts, a caller that needs a work item taken part of the way (`workItemAt`, `hasLiveWorkItem`, `canFastSkipAllRowGroups`) asks the chain for it and waits for the chain's cursor of that stage, parked. Tests: `FetchStepYieldTest`, which checks that every read of a column's pages ran on a virtual thread; `PoolWaitTest`, which holds back every read of a file not in memory until the pool has gone idle; `IndexWindowTest`, `FileMetadataCacheTest`.

4. **Only reads do I/O.** Every `InputFile` access during a read happens on a read's virtual thread, on the thread that slices an in-memory file, or on a caller off the read (the first footer, a later footer a caller loads); page tasks work on bytes the fetch step resolved ([FETCH_PLANNING.md](FETCH_PLANNING.md#fetch-plans)), and submission and publishing touch no file. Closing a column interrupts no thread: interrupting a thread inside a `FileChannel` operation closes the channel for every reader sharing it ([INPUT_FILES.md](INPUT_FILES.md#contract)). A change that interrupts a thread running a fetch step, or gives a page task file access, breaks that.

5. **A task of the pool never waits for work queued on the pool.** A fetch step and the planning chain run on the pool, and a pool of n threads whose n threads each wait for a task queued behind them stops. On a thread of the pool, `HardwoodContextImpl.decode` and `compute` run in place. Nothing on the pool waits for the planning chain: a step yields on its cursor, and a chain queued at the tail while a column waits is resubmitted at the head. The chain waits for no footer load another thread runs, such as the caller asking for a later file's metadata, whose parse that thread hands to the pool: it yields on the load (`FileMetadataCache.fileNeed`). A wait for a queued task on a thread of the pool breaks that. Tests: `MetadataParseThreadTest`, `HardwoodContextDecodeTest`, `NestedFillThreadTest`, `FileMetadataCacheTest`; a wait on queued work outside the decode and compute paths is untested.

6. **No monitor is held across a wait.** The speculative reads are virtual threads, and so may be the calling thread, and on JDK 21 a virtual thread that blocks inside `synchronized`, or waiting to enter it, holds its carrier. A thread that holds a monitor while it waits for I/O or for another virtual thread could leave the threads it waits for no carrier to run on. Every lock a read takes that a virtual thread may wait on is therefore a `ReentrantLock` (a `FetchSequence`'s, the planning chain's cursor, `RangeBackedInputFile`'s). A `synchronized` block around a fetch, or around a wait for another virtual thread, breaks that. Untested: the build runs on a JDK whose virtual threads do not pin on monitors.

7. **Speculative work fails a read only where the read reaches it.** A data entry read ahead of demand that fails is read again on demand, charged to nothing, and the demand read's failure goes to the step. A planning failure, a planning entry's read or a footer's among them, ends planning at the work item or file it hit: the planning chain keeps it, and every column that reaches that work item, or any after it, takes the same instance, so a file ahead that cannot be read fails the read only there and every row before it is returned first. A planning entry is not read again: the row group cannot be read either way. A failure no caller waits for is reported: a data read's or a footer read's is logged at `DEBUG` as it fails, and an `Error` is thrown once by the read's close, the `PrefetchTasks`' for a read no step or load took (`PrefetchTasks.recordUntaken`) and the planning chain's for a planning failure no column took.

8. **Every wait is released by its waker.** A fetch stopped for room in its queue, a fetch step stopped on a read, which the read's completion queues again whether it succeeds or fails, a close's wait for the read's tasks, and the consumer's poll each re-check a monotone condition, and every change of that condition queues a fetch step, signals the read's waiting threads (`ReadTasks.signal`) or hands its queue an element. The end of a stream offers the exchange's end-of-stream sentinel after setting its flag, and draining a closed exchange leaves the sentinel in its queue, so a consumer still waiting when the offer found the queue full, or when a close on another thread drained it, takes an element. A change that alters a wait's condition without that signal leaves the thread parked, or the fetch stopped, forever. A column has at most one fetch step queued or running, which holds a claim; a change raises a flag before it tries the claim, and a step that stops for room releases the claim before it reads the flag, so a change either finds the claim free and queues a step or is seen by the step that holds it. Every wait is untimed. A column's close stops the read and waits until no fetch step or page task of the read is in flight, the last of which signals; a close counts itself as a task while it stops the read, so a reader and its parent closing one read on two threads both wait until the read is stopped and quiescent, and a closer of the reader waits until the claimed close has completed (`CloseClaim`). A task that ends its column, such as a fetch step the closed context refuses, publishes the column's failure or end before it stops being counted, since a poll on a context of zero threads that found the read idle first would report a stall. Tests: `ScheduledColumnCloseTest`, `ReaderCloseLatencyTest`, `ReaderEofLatencyTest`, `BatchExchangeTest`, `BatchExchangeRowLimitTest`, `ZeroThreadContextTest`.

9. **A context's pool runs its tasks in arrival order, apart from the work a thread waits for.** A column's fetch step, the planning chain while a column or a caller waits for it, and a decode or `compute` a thread off the pool blocks on, go to the head of the queue (`DecodeExecutor`); every other task, page tasks and the planning chain planning ahead among them, runs in the order it arrived. The pool has one queue for every read and writer on the context, so a small read beside a full scan waits behind the scan's read-ahead. A read that needs a latency of its own beside other reads uses a context of its own, and the operating system shares the cores between the contexts' pools; an engine that reads splits in parallel on threads of its own uses a context of zero threads. The pool is the context's own: a caller-supplied executor is not supported, since a read waits for pool work, and reads issued from tasks of a bounded executor would starve it. Tests: `HardwoodContextDecodeTest`.

## A context of zero threads

`HardwoodContext.create(0)` and `builder().threads(0)` create a context without a pool. Each read on it keeps its fetch steps, page tasks and planning chain in a queue of its own (`ReadQueue`), created by its `RowGroupIterator` and shared with its `ReadScheduler`. The queue is the read's `ReadExecutor`, as the pool is on a context with one, and keeps the order the pool's queue gives: a fetch step, and the chain while a column waits for it, at the head, a page task and the chain planning ahead at the tail. Every queue item is one the pool would run, so nothing of the read changes but the thread: placement, cells, fills, publishing, the scheduler's order and its cap run as [READ_PIPELINE.md](READ_PIPELINE.md#scheduled-columns) describes, the thread driving the read counting as one decode thread.

The threads using the read run the queue. A poll that finds no batch (`BatchExchange.drive`) runs the item at the head and looks again; a column's close and the close of the planning chain run it while they wait for the read's work to end. A thread that finds the queue empty parks until the read signals (`ReadTasks`), which every item queued, every item ended, the last fetch step or page task of the read ending, and every publish, finish or failure of the read's exchanges does. `BatchWait` spans the park, which waits for a read in flight, a fetch step's or the planning chain's. The read counts its fetch steps and page tasks queued or running, a step yielded on a read or on a task's end among them (`ReadTasks`). A poll that finds no batch and none of them fails with an `IllegalStateException` instead of parking: nothing could publish a batch any more, which only a lost wake-up in Hardwood brings about.

`compute` and `decode` run in place on any thread, and `requireOffPool` never fails. **Invariant: on a context of zero threads no virtual thread a read starts runs `compute` or `decode`.** A caller that drives a read from a virtual thread of its own decodes on it, holding its carrier for each decode. The planning chain runs as items of the read's queue, and as on a pool never waits: its reads run on virtual threads, and the consumer parks while they are in flight. A read of files in memory starts no thread: it plans no row group ahead, which on one thread would only reorder its work, and its fetch steps run the chain in place. A read of files not in memory keeps its speculative reads, its footer reads and its planning ahead as on a pool. A writer on such a context appends and encodes on the calling thread ([WRITER.md](WRITER.md#threading)). `HardwoodContext.executor()` throws `UnsupportedOperationException`.

The `zero-threads` Maven profile runs the core test suite a second time on contexts of zero threads, through the internal `hardwood.internal.zeroThreads` property, minus the tests tagged `pool`, which pin how work spreads over a pool's threads or rely on a read's work running while no thread drives it; it runs on demand, for changes to how a read or a write is driven. Tests: `ZeroThreadContextTest`.

## Writes

A writer runs on the same pool and the caller's thread: each slice of a batch is appended one column per task, and at flush the column chunks are encoded and compressed one per task, with the caller claiming work too ([WRITER.md](WRITER.md#threading)). A writer's task never waits for a task queued on the pool: a chunk's thread waits only for a page body a worker has claimed, and an append worker waits between slices for the caller, spinning and then parked, for a bounded time before it returns its pool thread. A writer and readers can therefore share a context. On a context of zero threads the caller appends and encodes alone.

## Boundaries

- **Reads off a read.** The reads a caller makes outside a read, the first file's footer, a later footer a caller loads and the CLI's direct reads, call the `InputFile` on the caller's thread, outside any read's `PrefetchTasks`.
- **No bound on requests in flight, and demand bytes uncharged (#1687).** A context holds no budget on requests across its reads, and a read's demanded and next-unit entries, each up to S, are charged to no budget.
- **Decode concurrency per read (#1573).** The pool size is the only bound on a read's decode concurrency, and a consumer-bound read uses as many threads as the read-ahead cap admits pages for.
- **Pinning on JDK 21.** Invariant 6 exists because a virtual thread on JDK 21 holds its carrier while it blocks in or on a monitor. On a baseline of JDK 24 or later (JEP 491) virtual threads do not pin on monitors, and the rule and the `ReentrantLock`s it requires can go.
- **A warm page cache.** A file in memory includes a mapped local file (`MappedInputFile`), whose slices a fetch step and a page task read directly. Invariant 3 holds for it only while its pages are in the page cache: on a cold cache each first touch of a page faults on a thread of the pool, or on a context of zero threads on the thread driving the read (#1661).
