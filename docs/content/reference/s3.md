# S3 Reference

Options and behavior of the `hardwood-s3` module; [Reading from S3](../how-to/s3.md) shows how to use it.

## `S3Source` builder options

| Option | Default | Effect |
|--------|---------|--------|
| `region(String)` | — | AWS region. Required unless `endpoint` is set. |
| `endpoint(String)` | — | Custom endpoint for S3-compatible services (R2, GCS HMAC, MinIO). Region may be omitted when set. |
| `pathStyle(boolean)` | `false` | Path-style addressing, for services that require it (MinIO, SeaweedFS). |
| `credentials(...)` | — | Static `S3Credentials`, an `S3CredentialsProvider`, or the AWS chain via `hardwood-aws-auth`. Required. |
| `connectTimeout(Duration)` | 10s | Maximum time to establish a TCP connection. Ignored when a custom `httpClient` is supplied. |
| `requestTimeout(Duration)` | 30s | Maximum time for an individual HTTP request to complete. |
| `maxRetries(int)` | 3 | GET, part-upload, and abort retries on transient failures (HTTP 500, 503, network errors), with exponential backoff and jitter. Each publication-verification or uncertain-part cleanup sequence has a shared budget of `maxRetries + 1` attempts. `0` allows one attempt. Initiation, whole-object PUT, and completion are never automatically replayed. |
| `uploadPartSize(int)` | 8 MiB | Payload buffer size for each active output. Valid range: 5 MiB through `Integer.MAX_VALUE - 8` bytes, inclusive. Rejected immediately with `IllegalArgumentException` outside that range. Does not affect input ranges, Parquet pages, or row groups. |
| `httpClient(HttpClient)` | internal | Caller-supplied client for full transport control. The caller is responsible for closing it; `S3Source.close()` will not. |
| `rangeBacking(RangeBacking)` | `RangeBacking.NONE` | Whether files opened from this source cache the byte ranges they fetch. See [Range backing](#range-backing). |
| `tempDir(Path)` | `java.io.tmpdir` | Directory holding the sparse backing file under `RangeBacking.SPARSE_TEMPFILE`. Ignored under `RangeBacking.NONE`. |

When the retry budget is exhausted, the read fails with an `IOException`. For an HTTP error
status the message has the form `Failed to open s3://<bucket>/<key>: HTTP <status> <body>` when
opening the file and `Failed to read range [<start>, <end>) from s3://<bucket>/<key>: HTTP <status> <body>`
for a range read; for network errors the original `IOException` message is preserved.

A range read must be answered with HTTP 206. An endpoint that ignores the `Range` header and
answers HTTP 200 with the whole object makes the read fail with an `IOException` whose message
has the form `Failed to read range [<start>, <end>) from s3://<bucket>/<key>: HTTP 200, expected 206; the endpoint ignored the Range header`.

## Writing

`S3Source` creates outputs for `ParquetFileWriter`:

| Factory | Result |
|---------|--------|
| `outputFile(String bucket, String key)` | A new uncreated `OutputFile` for the bucket and key. Both must be non-null and non-empty. |
| `outputFile(String uri)` | A new uncreated `OutputFile` from `s3://bucket/key`. The prefix, bucket, and key are required. |

Null arguments throw `NullPointerException`; empty arguments or invalid URI shapes throw `IllegalArgumentException`. Factories perform no network I/O. `create()` allocates the output buffer and generates a write UUID without contacting S3. `ParquetFileWriter.create(...)` calls it automatically.

Keys are literal object names: spaces, Unicode, `+`, `%`, `?`, `#`, repeated `/`, and `..` are preserved. The URI overload takes everything after the bucket's first `/` as the key without URI decoding or path normalization. For example, `s3://bucket/a%20b` addresses the literal key `a%20b`, not `a b`.

### Buffering and limits

Each active output holds one `uploadPartSize` byte array, allocated on `create()`. The array is reused across sequential uploads. No output data is staged on disk; `rangeBacking` and `tempDir` affect reads only. The writer's row groups, page indexes, Bloom filters, and footer metadata consume additional memory.

Outputs smaller than the part size use one whole-object PUT on close, including empty outputs. Reaching the part size starts a multipart upload immediately. Full parts upload sequentially; close uploads any final non-empty part and completes the upload. Part boundaries are independent of Parquet page and row-group boundaries.

An output supports at most 10,000 parts and at most `10,000 * uploadPartSize` bytes: 78.125 GiB with the default 8 MiB buffer. The endpoint may impose additional limits. A write exceeding the output limit fails with `IOException` before consuming that call's input or uploading more parts. The output then rejects further writes and cannot be resumed. The maximum accepted buffer size does not guarantee enough heap to allocate it.

### Publication and cleanup

The bucket must already exist. Keep `S3Source` open until its outputs finish or are discarded. Outputs do not close the source or its HTTP client. Each output is single-use and must be written sequentially; simultaneous writes to the same output are unsupported.

A successful close confirms publication of the complete object. Publication replaces any existing object at the key; there is no conditional-write or version-management option. Before publication, uploaded parts do not replace an existing object. Acknowledged publication sends no verification HEAD request.

Each output stores a fresh UUID in the reserved object metadata header `x-amz-meta-hardwood-write-id`. The UUID remains stable across its part retries and verification checks. This metadata is independent of Parquet key-value metadata and does not change the file's bytes or key. It identifies a write attempt; it does not lock the key or prevent another writer from replacing it.

When a publication response is uncertain, close checks the object's metadata with HEAD before aborting a known upload. Exactly one matching write UUID and a matching full object length confirm publication; close then succeeds. Missing, old, replaced, or malformed metadata cannot confirm success. HEAD 404, 500/503, network failures, and nonmatching metadata share the same `maxRetries + 1` check budget with exponential backoff and jitter. Other HEAD statuses, including permission denial, stop verification as inconclusive. Verification reads metadata only.

If publication remains unconfirmed, the original exception is thrown with a suppressed diagnostic containing the write UUID, expected length, verification result, and HEAD-attempt count. The completed object may exist. Verification and cleanup failures are also suppressed on the original exception. A missing multipart upload does not establish whether publication succeeded. Definitive validation or permission failures are not recovered as success by matching metadata.

Failed writes reject further data and release local payload storage. Discard aborts only this output's known upload ID and never deletes the destination object. If a part request has an uncertain outcome, cleanup uses bounded abort/ListParts checks and requires `NoSuchUpload` to confirm removal. A lost initialization response can leave an upload whose ID is unknown, which the output cannot abort. Cleanup failures can leave pending parts; bucket lifecycle rules can expire abandoned uploads.

Interruption stops publication verification and attempts bounded cleanup while preserving the interrupt flag. A repeated close never republishes or restarts verification. After an unresolved cleanup failure, an explicit `discard()` may retry cleanup of the known upload. Discard after a successful close does nothing.

### Write permissions

For AWS S3, upload operations require `s3:PutObject`; cleanup requires `s3:AbortMultipartUpload`, with `s3:ListMultipartUploadParts` for uncertain-part cleanup checks. HEAD verification requires `s3:GetObject` on the destination. `s3:ListBucket` controls whether a missing object returns 404 or 403; a 403 remains inconclusive. See the AWS [multipart permissions](https://docs.aws.amazon.com/AmazonS3/latest/userguide/mpuoverview.html#mpuAndPermissions) and [HEAD permissions](https://docs.aws.amazon.com/AmazonS3/latest/API/API_HeadObject.html).

Upload-only credentials can publish successfully when the response is acknowledged, but may not confirm publication after a lost response. There is no permission preflight on create. The caller supplies credentials and provisions permissions. S3-compatible endpoints must support the upload, multipart, metadata, and cleanup operations used here; their permission models may differ.

## Footer pre-fetch

`open()` issues one GET for the last 64 KB of the object, or the whole object if it is
smaller. That single round-trip discovers the object size, so there is never a
separate HEAD request. Those bytes are kept for as long as the file is open, and any
read falling entirely inside that trailing window is answered without a further
request. An HTTP 200 answer to this GET is accepted: the whole object then forms the
window, and no read goes to the network again.

For most files the window also carries the Parquet footer, which is why opening a
file usually costs one GET. It is a cost heuristic rather than a guarantee: footer
size grows with row groups × columns and with the size of the per-column statistics,
so a wide schema, a heavily split file, or long string min/max values can push the
footer past 64 KB. Reading it then costs one extra GET. When the context's `MetadataSource`
supplies the footer, the open reads only the 8-byte trailer, which lies in the window, so that
extra GET is not made.

The `ETag` header of this response is the object's `InputFile.identity()`, quotes included. It is
empty when the endpoint sends no `ETag`.

This applies to every `S3InputFile`, independent of the range backing below.

## I/O behavior

Hardwood coalesces the column chunk reads within each row group into as few HTTP requests as
possible. The page index of the columns a read uses is fetched for several row groups at a time,
one request for the offset indexes and, on a filtered read, one for the column indexes and one
for the bloom filters it checks; a filtered read may add one request per dictionary it checks.
Column projection, page-level predicate pushdown,
and `head(n)` on an unfiltered read narrow the byte ranges before coalescing.

Without a row limit, the reader fetches all projected (and filtered) column data for an entire
row group when any column enters it, even if the consumer stops reading early. `head(n)` on the
`buildRowReader()` builder truncates each column's fetch to the pages covering the needed rows.
With a filter, `head(n)` counts matching rows, which are not known before the pages are decoded,
so it does not narrow the fetch.

## Range backing

`RangeBacking` sets whether an `S3InputFile` also keeps the bytes it fetches outside
that window:

| Value | Behaviour |
|-------|-----------|
| `NONE` (default) | Nothing beyond the footer pre-fetch is kept. Every other non-empty `readRange` issues an HTTP GET, including a repeat read of a range already fetched. |
| `SPARSE_TEMPFILE` | Fetched ranges are written into a sparse temp file mmapped into the process. A read covered by already-fetched bytes is served from the mapping with no HTTP GET; a read spanning a gap fetches only the missing sub-ranges. |

The value changes how many HTTP requests go out; both give the reader identical bytes.
The cache is per `S3InputFile` and lives until that file is closed.

`SPARSE_TEMPFILE` applies to a whole `S3Source`, so it suits workloads that re-read
the same byte ranges; `hardwood dive` opts in for every file it opens. Its
properties:

- Disk and memory footprint scale with bytes fetched, not with file size, on
  filesystems that support sparse files (ext4, xfs, apfs, ntfs).
- Files larger than `Integer.MAX_VALUE` bytes (2 GB) cannot be range-backed; `open()`
  throws an `UnsupportedOperationException` naming the limit. Read those with `RangeBacking.NONE`.
- The backing file is created in `tempDir`, which must exist and be writeable with
  room for the worst-case bytes fetched per file. `S3Source.builder().build()` rejects
  a directory that is missing or not writeable.
- `close()` deletes the backing file, but the mapping behind it is released by the
  garbage collector, so the address space outlives the `close()` call. On Windows, where a
  mapped file cannot be deleted, the file itself also outlives it, until JVM exit.

## Fetch-cost counters

Each `S3InputFile` tracks the network I/O it has performed since `open()`:

- `networkRequestCount()` — HTTP GET requests issued: the [footer pre-fetch](#footer-pre-fetch)
  plus every column-chunk range fetch. Reads answered from the pre-fetched footer window
  are not counted, nor are reads answered from the cache under
  `RangeBacking.SPARSE_TEMPFILE`.
- `networkBytesFetched()` — total bytes fetched across those requests, counted the same way.

Read the counters before the try-with-resources block exits, while the `S3InputFile` is still open.

## Not supported

- **Anonymous (unsigned) requests** — `S3Credentials` requires an access key + secret key pair;
  there is no built-in mode for public buckets without credentials.
- **Requester-pays buckets** — Hardwood does not send the `x-amz-request-payer` header. Reads
  against requester-pays buckets will fail with `403 AccessDenied` even with valid credentials.
